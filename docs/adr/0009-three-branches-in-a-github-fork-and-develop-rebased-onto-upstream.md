# The fork is a GitHub fork with three branches, and `develop` is rebased onto upstream

Since ADR 0005 the repository `BuckanovNikita/cvat-fork` held upstream's full source joined to the earlier overlay's history by one merge: `main` carried 194 overlay commits, the whole of upstream and the fork's work, and a release was to be taken with `git merge <tag>`. Two things did not fit. The join cannot be rebased, so the fork's changes could never be read as a short line of commits on top of a release. And there was no branch holding only what the fork distributes: evidence of runs on one machine, a superseded local tracker and a test stack bound to one cluster sat beside the product in every revision a downstream could take (ADR 0008).

On 2026-11-19 the owner decided to give the fork an ordinary fork's shape, in a new repository so that nothing published is rewritten. `BuckanovNikita/true-cvat` is a GitHub fork of `cvat-ai/cvat` with three branches:

- **`main`** is the upstream release the fork is on, `v2.82.0`, and nothing else. It only ever fast-forwards to a later upstream release.
- **`develop`** starts from `main` and is the fork's work as a line of commits without a merge. It is the default branch and the base of every task branch. When a release is taken, `develop` is rebased onto the new `main`.
- **`release`** is what the fork distributes: `develop` without `local/`. Each release is a merge commit on `release` whose second parent is the `develop` commit it was cut from, tagged `v<upstream release>.<n>`.

Everything that belongs to the machine the fork is developed on, or to its past work, lives in one directory, `local/`: the dated evidence, the local tracker used until 2026-11-17, the infrastructure migration note and the Kubernetes test stack. None of it is secret, so it stays in `develop` and its history; `release` drops the directory and nothing else. The agent instructions (`AGENTS.md`, `CLAUDE.md`, `docs/agents/`, `skills-lock.json`), the checks (`verify/`, `tools/gate/`, `prek.toml`, `ruff.toml`) and the documents under `docs/` ship.

`develop` was built from `cvat-fork`'s published work without replaying it: one commit per landing on `cvat-fork`'s `main` since the join, each with the tree, author, date and message of the commit it stands for and a `Landed-as:` trailer naming that commit. A pull request number in a subject is written with its repository, `BuckanovNikita/cvat-fork#3`, so that GitHub does not link it to a pull request of this one. The first three stage tags mark three of those landings: `v2.82.0.1` the full-source fork with Team Analytics inside the backend, `v2.82.0.2` Team Analytics for administrators with settings and the server image from public bases, `v2.82.0.3` the parameterised builds and the fork's two charts.

This supersedes ADR 0005's decision to join the histories by a merge and to take releases with `git merge <tag>`. It is the option ADR 0005 kept as a fallback "only on the owner's word", carried out beside the published branch instead of over it.

## Considered Options

- **Force-pushing a rebuilt `main` in `cvat-fork`.** One repository and one address. Rejected: it replaces a published branch, and the downstream records what it deployed by a fork revision of that branch (ADR 0008).
- **A new repository without the fork relation.** Nothing of upstream's is copied by GitHub. Rejected by the owner: a fork states where the source comes from and lets a change be offered to upstream.
- **Carrying the old history into `develop`.** Every old revision keeps its identifier. Rejected: the join is exactly what cannot be rebased onto a later release.
- **A `release` with no `develop` in its ancestry, one snapshot commit per stage.** A clone of `release` would carry no development history. Not needed: nothing in `develop` is private, and a merge records which `develop` commit a release was cut from.
- **Cleaning `release` by a list of paths.** No file would move. Rejected by the owner in favour of one directory: the rule "`release` is `develop` without `local/`" needs no list to maintain and is checked with one diff.
- **Fork version numbers in the product.** `2.82.0.1` in `cvat/__init__.py`, the chart and `package.json`. Rejected: upstream's release tooling, Helm and npm accept three parts only, and the tags are meant to mark stages of work, not to version an artefact.

## Consequences

- `cvat-fork` is the frozen record of the fork's earlier history. Its revisions are not ancestors of anything in this repository; the `Landed-as:` trailers and the [migration evidence](../../local/evidence/2026-11-19-true-cvat-migration.md) map them. A document or an evidence file that names a `cvat-fork` revision names it there.
- Paths moved: `docs/evidence/` is `local/evidence/`, `.scratch/` is `local/scratch/`, `verify/team-analytics-stack/` is `local/team-analytics-stack/` and `INFRA_MIGRATION.md` is `local/INFRA_MIGRATION.md`. The moved records are not rewritten, so their own links and the citations inside them still use the old paths; [`local/README.md`](../../local/README.md) has the mapping. Two comments in `cvat/apps/team_analytics/` cite `docs/evidence/` and were left as they are, because the downstream vendors those files.
- A shipped document that links into `local/` has a link that resolves on `develop` and not on `release`.
- `develop` has no merge commits. A pull request is merged by squash or by rebase, and the repository does not offer a merge commit. A release of upstream is not delivered by a pull request: the rebased branch is pushed for review, and the owner moves `main` by a fast-forward and replaces `develop` with `--force-with-lease`, the one forced push the fork allows ([upgrade procedure](../upstream-upgrade.md#5-record-and-hand-off)). Open task branches are rebased afterwards.
- `release` is cut by taking `develop`'s tree as it is and removing `local/`, not by merging contents, so cutting cannot conflict and is unaffected by a rebase of `develop`. After a rebase the previous copies of `develop`'s commits stay reachable from `release`; that is accepted.
- The stage tags `v<upstream release>.<n>` change no version string, chart version or image tag, and no GitHub Release is created for them. `n` starts at 1 for each upstream release. The image tags the build scripts default to (`…-fork`) are unchanged.
- The repository is a GitHub fork, so GitHub and `gh` take the parent, `cvat-ai/cvat`, as the default target of a pull request. Every pull request names this repository and `develop` explicitly ([delivery rules](../agents/issue-tracker.md#delivery)); the fork's work is never opened against upstream by accident. "Sync fork" is never used: it would merge upstream's `develop` into the fork's.
- `main` carries upstream's `.github/`. GitHub Actions is disabled in the repository, so those workflows do not run; `develop` and `release` do not have the directory. Enabling Actions for a workflow of the fork's own first needs a way to keep upstream's from running on `main`.
- What ADR 0005 said beyond the join still holds. Upstream owns the root names: its `README.md` stays as upstream wrote it and the fork's Russian text is `README.fork.md`, a stated exception to the rule that `README.md` is Russian. The fork's entries are appended to upstream's `.gitignore`, and the gate's Python pin lives in `tools/gate/`. Upstream's `.github/` is removed on `develop`; a release that changes a file there conflicts with the deletion during the rebase and the answer is to keep it deleted, and a file a release adds there is removed. Upstream's whole-repository linters are not run as upstream runs them; the fork's gate checks the fork's files. Compose stays unsupported. The `upstream` remote has no default fetch rule and tags are fetched by name. The tags `cvat-v2.74.1`, `cvat-v2.82.0` and `cvat-v2.82.0-widened` exist in `cvat-fork` only.
- The compatibility surface of ADR 0008 is unchanged by this decision, and the downstream now has a name for what it takes: a stage tag on `release`. A later change to that surface keeps the rule ADR 0008 set: every input a closed network has to supply is an argument with a public default, read from the environment by the build scripts, so the same files build in public and behind a package mirror with no route to the internet.
