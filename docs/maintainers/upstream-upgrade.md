# Upstream upgrade

Moving the fork onto a new upstream release. Every push in it needs the owner's word.

1. Record the start once (never re-run to resume): `git fetch origin && git update-ref refs/upgrade/base origin/main && git update-ref refs/upgrade/start origin/develop`. The `upstream` remote (`https://github.com/cvat-ai/cvat.git`) has no fetch refspec; fetch tags by name: `git fetch --filter=blob:none --no-tags upstream refs/tags/<tag>:refs/tags/<tag>`.
2. Rebase: check `git merge-base --is-ancestor refs/upgrade/base "${TARGET}^{commit}"` and no merges in `refs/upgrade/base..refs/upgrade/start`; `git switch -c upgrade/cvat-${TARGET} refs/upgrade/start && git rebase --onto "${TARGET}^{commit}" refs/upgrade/base`. Commits landing on `develop` meanwhile are cherry-picked (never merged) after the rebase finishes, with the upgrade branch checked out: `git fetch origin && git cherry-pick refs/upgrade/start..origin/develop && git update-ref refs/upgrade/start origin/develop`. The update-ref runs only when every pick applied; on a conflict resolve, `git cherry-pick --continue`, then run the update-ref alone without fetching again. `refs/upgrade/start` must only ever name a `develop` commit whose whole history the upgrade branch carries, or step 5 replaces `develop` without the missing commits. Expected conflicts: the edited UI files, both policies and their CSVs, `.github/` (keep deleted; remove files the release adds there in a final commit), appended tails (upstream lines, then the fork block), `helm-chart/` and `Dockerfile.ui` args (keep every published name). A `helm-chart/Chart.yaml` conflict keeps the fork's dependency set (no nuclio dependency); when upstream's dependency version line moves, re-copy the tarball into `charts/` and update `Chart.lock`.
3. Check the policies and update the images: `git diff "${TARGET}" HEAD -- cvat/apps/engine/rules` must show only the two marked additions and added CSV rows; compare helper policies; review new scopes. Bump `v2.82.0` defaults together (`git grep -n -F v2.82.0` over fork files): `build-ui.sh`, `build-server.sh`, `tools/gate/ui-lint.sh` (`UPSTREAM_TAG`), `verify/policy_test.sh` (`STOCK_TAG`), `verify/policy_bundle.sh`, `verify/team_analytics_backend.sh`, the stack's `stack.env` and `run.sh`. Port `git diff <old> "${TARGET}" -- Dockerfile` into `Dockerfile.server` (Ubuntu package names -> Debian 12, keep commented deviations, new COPY paths into `COPIED`, new bases when versions move), then set `PORTED_FROM_SHA256` to `sha256sum Dockerfile`. Rebuild both images.
4. Verify the integrated changes: run every command of "Checks" in [AGENTS.md](../../AGENTS.md), the out-of-band checks, the bundle check against the new image, and a stack `cycle`. Read the release's changes to the upstream internals listed on [Team Analytics internals](team-analytics.md):

   ```bash
   git diff v2.82.0 "${TARGET}" -- cvat/apps/iam/permissions.py cvat/apps/iam/middleware.py \
       cvat/apps/redis_handler/management/commands/syncperiodicjobs.py cvat/settings/base.py cvat/requirements \
       cvat/apps/iam/models.py cvat/apps/engine/models.py cvat/apps/organizations/{apps.py,default_settings.py,permissions.py,rules/organizations.rego} \
       backend_entrypoint.sh backend_entrypoint.d helm-chart/templates/_helpers.tpl helm-chart/templates/cvat_backend \
       cvat-core/src/server-proxy.ts cvat-core/src/axios-config.ts cvat/apps/iam/rules/tests/generate_tests.py
   ```
5. Hand off (owner's word only): verify `origin/main` == `refs/upgrade/base` and `origin/develop` == `refs/upgrade/start`, review with `git range-diff refs/upgrade/base..refs/upgrade/start "${TARGET}..upgrade/cvat-${TARGET}"`, then `git push --atomic --force-with-lease="develop:$(git rev-parse refs/upgrade/start)" origin "${TARGET}^{commit}:refs/heads/main" "upgrade/cvat-${TARGET}:develop"` (the only forced push allowed) and delete both `refs/upgrade` refs. Afterwards refresh local branches (`git fetch origin main:main`; `git switch -C develop origin/develop` once `git log origin/develop..develop` holds nothing wanted) and rebase open task branches onto the new `develop`. Before an authorized deployment keep the previous UI and server images and the deployment configuration, and plan the database backup and rollback for the target release: moving branches back does not undo DB migrations.
